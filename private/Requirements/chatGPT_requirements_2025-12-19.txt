1. Ce que fait réellement QReader (partie pré-traitement)

QReader n’est pas un moteur de décodage. Il s’appuie sur :
	•	pyzbar / zbar pour la lecture effective du QR code
	•	et ajoute une couche de pré-traitement adaptatif pour maximiser le taux de détection.

Les étapes clés côté image sont (simplifié mais fidèle) :

1.1 Pipeline général

Pour une image donnée, QReader :
	1.	génère plusieurs versions transformées de l’image
	2.	tente le décodage sur chacune
	3.	s’arrête dès qu’un QR est détecté

1.2 Transformations appliquées

Typiquement :
	•	conversion en niveaux de gris
	•	ajustement de contraste (global ou adaptatif)
	•	binarisation (seuil fixe ou adaptatif)
	•	sharpening léger
	•	redimensionnement (upscale / downscale)
	•	parfois inversion noir/blanc
	•	parfois crop ou padding

Il n’y a pas de ML, pas de CNN, pas de heuristique opaque.

👉 C’est donc 100 % portable conceptuellement.

⸻

2. Est-ce raisonnable de porter cette partie en Go ?

Réponse courte : oui, totalement, et sans perte fonctionnelle.

Pourquoi c’est faisable
	•	Tous les traitements utilisés sont des opérations classiques de vision par ordinateur
	•	Aucun dépendant de NumPy “avancé”
	•	Pas de logique Python spécifique (pas de generators, pas de métaprogrammation)

Pourquoi ça vaut le coup
	•	Suppression de Docker + Python
	•	Moins de latence (appel direct en Go)
	•	Meilleure intégration avec ton pipeline Go
	•	Contrôle fin de la mémoire et du parallélisme

⸻

1. Quel rôle joue YOLOv8 / PyTorch dans QReader

D’après la documentation du dépôt :
	•	QReader combine deux composants :
	•	un modèle YOLOv8 entraîné pour détecter et segmenter les QR codes
	•	et le décodage Pyzbar classique.  ￼
	•	Le modèle YOLOv8 est utilisé pour la détection de QR dans l’image.
	•	Il ne décode pas le QR, il localise/segmente la zone probable du QR.  ￼
	•	L’image est ensuite recadrée ou pré-traitée autour de la détection, puis
la lecture du contenu est tentée avec Pyzbar via divers pré-traitements.  ￼

⸻

2. Comment fonctionne YOLOv8 dans le contexte Python
	•	YOLOv8 (et ses variantes comme yolov8n, yolov8s, etc.) est une famille de modèles de détection d’objets…
	•	conçue pour fonctionner avec PyTorch / Ultralytics.  ￼
	•	Dans QReader, la dépendance Python à YOLOv8 implique :
	•	la librairie Ultralytics YOLOv8
	•	un modèle .pt (format PyTorch) chargé à l’initialisation
	•	un moteur d’inférence PyTorch (CPU ou GPU)
	•	potentiellement la librairie torch elle-même, ce qui peut exiger l’installation de PyTorch.  ￼

⸻

3. Dépendances de QReader (relevées dans les manifestes)

D’après les informations publiques et les métadonnées PyPI :
	•	Python :
	•	opencv-python, numpy, pyzbar
	•	qrdet (le module qui intègre le modèle YOLOv8)  ￼
	•	qrdet est un module distinct fournit par le même auteur pour la détection YOLOv8 :
	•	il dépend directement de Ultralytics YOLOv8
	•	ce qui signifie des dépendances sur PyTorch.  ￼

Donc QReader ne se contente pas d’un simple modèle exporté comme ONNX :
il utilise bien l’API PyTorch pour effectuer l’inférence du modèle de détection.  ￼

⸻

4. Difficultés que cela pose pour ton portage en Go

A. Portage de la détection YOLOv8

La partie YOLOv8 est un modèle entraîné de deep learning, ce qui pose plusieurs défis :

1) Chargement et exécution du modèle
	•	PyTorch est une dépendance Python lourde
	•	Pas trivialement utilisable depuis Go sans binding (CGO, C API ou autre)

2) Formats de modèles
	•	Le modèle .pt PyTorch n’est pas lisible nativement par les bibliothèques Go
	•	Il faudrait convertir le modèle dans un format utilisable (ex : ONNX, TensorRT, TFLite…)

3) Inference en Go

Options techniques :
	•	Utiliser ONNX Runtime avec Go
	•	ONNX Runtime a bindings Go
	•	mais nécessite que tu convertisses le modèle YOLOv8 → ONNX d’abord
	•	Utiliser TensorRT / OpenVINO / etc.
	•	mais ce sont des solutions lourdes, spécifiques à plate-forme
	•	Exporter le modèle et utiliser une dépendance CGO
	•	mais ce genre de liaison enlève l’intérêt d’un « pur Go » simple

=> en d’autres termes, le portage de la détection YOLOv8 seule est un travail significatif si tu veux le conserver.
Autrement dit, ce n’est pas un simple ensemble de fonctions image, mais un modèle neural complet.  ￼

⸻

B. Portage de la logique de pré-traitement

Cette partie est nettement plus simple :
	•	concerne des transformations classiques d’images (grayscale, threshold, etc.)
	•	déjà réalisables avec GoCV ou une autre librairie Go d’image

=> C’est celle-ci que tu peux porter en Go de façon réaliste sans dépendances externes lourdes.

⸻

C. Décodage Pyzbar

Tu as déjà indiqué que convertir le décodage (la lecture du contenu) est à traiter plus tard. Le portage de la détection est cependant un gant de fer comparé au pré-traitement.

	•	Utiliser des méthodes classiques de localisation de QR plus robustes que pyzbar seul

Chaîne technique

YOLOv8 (.pt)
   ↓ export
YOLOv8 (.onnx)
   ↓
ONNX Runtime (C)

Go
